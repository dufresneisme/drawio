## 三、推荐：直接新建工程，再移植功能

我的明确建议是：**新建一个干净的 MRS 工程，按上面的框架搭好骨架，然后把现有能跑的函数逐个移植过去。**

### 为什么不建议在旧工程上改？

旧工程（`CCB/ChargeControlBox`）存在太多“历史包袱”：

| 问题 | 说明 |
|---|---|
| **大量空文件** | 20 多个 0 字节文件，删除或保留都麻烦 |
| **命名混乱** | 文件名、文件头、include guard 三者不一致，改起来很碎 |
| **编译产物在仓库里** | `obj/` 目录提交了 .o/.elf/.hex，清理要.git操作 |
| **IDE 生成文件污染** | `.cproject`、`.mrs/snapshot`、`.launch` 等含绝对路径 |
| **目录结构已定型** | `Firmware/` 在工程外部，MRS 引用外部目录容易出问题 |
| **BSP 和 Firmware 职责混淆** | 改框架需要大量重构，不如在新工程里重新组织 |

在旧工程上改，很容易出现：
- 删错文件导致编译不过；
- 改到一半发现目录结构不支持；
- 空文件和半成品模块干扰判断；
- 版本管理混乱。

---

### 为什么建议新建工程？

1. **干净起点**：没有历史包袱，目录结构一开始就正确。
2. **MRS 友好**：`firmware/` 在工程内部，include path 好配。
3. **逐步移植**：每次只搬一个能跑的功能，验证通过再搬下一个。
4. **旧工程当参考**：旧代码随时能看，不会被破坏。
5. **可并行**：新工程搭骨架时，旧工程还能继续用。
