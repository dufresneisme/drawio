CHG控制盒工程框架记录
========================

文件用途
--------
本文件用于持续记录 ChargeControlBox 工程的框架设计、模块职责、调度方案、
关键取舍和后续约束。新增框架决策时，应在本文件中补充日期、背景、结论和影响，
不要只把结论留在聊天记录中。


一、任务调度方案对比（2026-09-21）
===================================

对比对象
--------
1. 旧版稳定工程：
   chargeControlBoxAllProject/stableRepos/chargeControllerBox
2. 当前新工程：
   001WCHCCB/CCB

共同结论
--------
两套方案都属于裸机下的协作式周期调度，不是 RTOS，也不是真正的时间片轮转。

普通任务由主循环调用。一个普通任务开始运行后，其他普通任务不能强制抢占它；
如果任务内部阻塞或执行时间过长，就会延迟其他主循环任务。

50~200 us 级别的短路保护、ADC 快速数据处理等硬实时路径不能依赖普通任务调度，
应放在 ADC DMA/注入转换中断或专用定时器中断中完成。


二、旧版稳定工程的调度方式
===========================

主要文件
--------
tools/TimeSliceOffset/timeSliceOffset.c
tools/TimeSliceOffset/timeSliceOffset.h
APP/businessLogic/Src/task.c
APP/functionalModule/Src/FM_TIM.c
APP/application/Src/start.c

工作过程
--------
1. 每个任务使用一个 STR_TimeSliceOffset 结构体，并注册到单向链表。
2. TIM16 每 1 ms 调用 TimeSliceOffset_Produce()。
3. 中断函数遍历链表，递减每个任务的 count；计数到期后置 runFlag。
4. 主循环 TimeSliceOffset_Start() 再遍历链表，执行 runFlag 已置位的任务。
5. 定时任务执行后清除 runFlag，并重新开始计数。
6. 主循环扫描结束后执行 __WFI()，等待下一个中断唤醒。

旧版的优点
----------
1. 支持任务动态注册和注销，适合旧工程中按状态启用的功能。
2. 支持 offset，可以把相同周期的任务错开，降低同一时刻的执行峰值。
3. 使用 __WFI()，没有任务执行时可以降低 CPU 空转和功耗。
4. 任务周期逻辑简单，已有较多业务任务使用过这种方式。

旧版的缺点和风险
----------------
1. 每 1 ms 的定时器中断都要遍历任务链表，中断开销随任务数量增加。
2. runFlag 只有“待执行/未待执行”两种状态。主循环繁忙时，多个已错过的周期会
   合并成一次执行，漏周期不会被明确统计。
3. 链表由主循环注册/注销，而中断同时遍历链表。若运行时修改链表，没有临界区
   保护，存在中断并发访问链表指针的风险。
4. 没有任务执行时间预算、最大执行时间和超时次数统计。
5. reloadVal 为 0 的任务会在每次主循环轮询时执行，若任务本身没有严格限制，
   可能长期占用主循环。


三、当前 CCB 工程的调度方式
============================

主要文件
--------
001WCHCCB/CCB/Firmware/App/Inc/app_scheduler.h
001WCHCCB/CCB/Firmware/App/Src/app_scheduler.c
001WCHCCB/CCB/Firmware/App/Src/app.c

工作过程
--------
1. 使用编译期确定的静态 AppTask_t 数组保存任务配置和运行统计。
2. TIM2 只维护 1 ms 系统 Tick，定时器中断不遍历任务，也不直接执行普通任务。
3. 主循环调用 AppScheduler_Run()，比较当前 Tick 和每个任务的 nextTick。
4. 任务到期后在主循环中执行，每次调用对每个任务最多执行一次。
5. 任务执行结束后统计本次运行时间、最大运行时间、超时次数和漏周期次数。
6. 如果任务已经错过多个周期，调度器跳过过期周期，不连续补跑，避免主循环越忙
   越产生补跑风暴。
7. 通信任务目前单独放在 APP_Run() 中，并限制每次调用处理量，避免一次处理过多
   数据长时间占用主循环。

当前方案的优点
--------------
1. 任务表静态分配，内存和任务顺序明确，适合嵌入式产品长期维护。
2. TIM2 中断只更新时间，避免在中断中遍历所有任务，有利于保护 ADC、DMA 等
   高实时性中断。
3. 能够统计任务运行时间、超时次数和漏周期次数，问题更容易定位。
4. 使用绝对 nextTick 计算周期，不会因为一次任务执行时间变长而永久产生周期漂移。
5. 任务执行顺序由静态表明确决定，便于评估最坏情况下的主循环负载。

当前方案的不足
--------------
1. 当前任务表还没有 offset/phase 配置；后续增加多个 1 ms、5 ms、10 ms 任务时，
   可能在同一时刻集中执行，需要补充首次延时或相位偏移。
2. 当前 APP_Run() 持续轮询，没有使用 __WFI()，CPU 空闲功耗高于旧版；但这也使
   DMA 通信数据可以被更快地消费，当前开发阶段可以接受。
3. 静态任务表不支持运行时增加任务；目前可以通过 enabled 启停任务，若以后确实
   需要动态任务，应增加受控的注册接口，而不是直接引入无保护链表。
4. 执行时间使用 1 ms Tick 统计，无法准确区分小于 1 ms 的任务耗时；精确测量时
   应使用 DWT 周期计数器或更高频率的硬件计时器。
5. maxRuntimeMs 只用于检测和计数，不能从外部强制打断正在运行的任务。因此它
   不是任务抢占机制，也不能替代任务内部的非阻塞设计。


四、两套方案的关键差异
=======================

项目                 旧版稳定工程                  当前 CCB 工程
--------------------------------------------------------------------------
任务保存             动态单向链表                  静态任务数组
任务触发             1 ms 中断倒计时并置标志       主循环比较绝对 nextTick
定时器中断工作量     遍历所有任务，O(N)            只更新时间，近似 O(1)
任务偏移             支持 offset                   当前暂不支持
漏周期               runFlag 合并，难以观察         统计 missedCount 并跳过补跑
超时统计             无                             有运行时间和超时次数统计
动态注册/注销        支持，但需处理并发风险         当前不支持动态增加
空闲处理             __WFI()                       持续轮询
确定性               受链表和动态操作影响           静态数组更容易评估
实时保护             不在普通任务中，使用 ADC 中断  不在普通任务中，使用 ADC 中断


五、当前工程的框架决策
=======================

1. 当前 CCB 继续使用“静态任务表 + 主循环轮询 + Tick 到期判断”。
2. 不直接复制旧工程的链表调度器；旧工程只作为功能和设计参考。
3. 后续在 AppTask_t 中增加 offsetMs 或 firstDelayMs，用于错开同周期任务。
4. 普通任务必须保持短小、非阻塞，并限制一次调用的处理量。
5. 串口 DMA 接收、ADC DMA 等中断只负责搬运数据、置位事件或记录状态；协议解析、
   数据聚合和非硬实时业务放到主循环任务中。
6. 短路保护的快速判断保持在 ADC 快速采样中断路径，不能改成依赖 APP 调度周期。
7. 任务超时统计用于诊断和后续保护策略，不把它误认为可以强制终止任务。
8. 后续若增加低功耗需求，再评估使用 __WFI() 或事件唤醒；必须先保证定时器、
   UART DMA、ADC DMA 等中断能够正确唤醒主循环并处理待处理事件。


六、后续调度实现顺序
=====================

1. 保持 TIM2 作为 1 ms 系统 Tick。
2. 保持 ADC 快速保护路径独立于普通任务调度。
3. 给任务表补充 offset/firstDelay 配置，并错开多个同周期任务。
4. 逐个加入测量、保护状态刷新、通信协议、存储和状态指示任务，记录每个任务的
   周期、预算和实际最大耗时。
5. 对所有任务检查是否存在 delay、while 等不可控阻塞。
6. 根据实际负载决定是否加入事件标志、任务优先级或低功耗等待机制。
